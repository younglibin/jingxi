# 本地文件方案部署与验证

版本1.2 · 2026-10-27。配套[主方案](../superpowers/specs/2026-10-27-portfolio-technical-design.md)和[字段与图片规则](data-api-contract.md)。取消关系数据库和数据库容器。代码运行方式见[本地 Docker 说明](../LOCAL_DOCKER.md)，实际验证结果见[开发记录](../testing/implementation-progress.md)。以下验收目标不等于已全部执行。

## 1 项目与运行目录

一台服务器部署Nginx、Next.js、Java三个容器，只有80/443公开。Java独占业务文件写入，Next.js不直接读写store.json，也不持有管理员密码。内存会话重启后失效，已保存业务数据从文件重新加载。

| 项目根目录下路径 | 用途 | 是否对外公开 |
| --- | --- | --- |
| storage/data/ | store.json、同目录写临时文件、进程文件锁 | 否 |
| storage/images/originals/ | 原图 | 否 |
| storage/images/display/ | 显示图 | 仅经Java按公开引用授权输出 |
| storage/images/tmp/ | 上传与缩图临时文件 | 否 |
| storage/backups/ | 本地备份包临时落点 | 否 |
| storage/logs/ | 应用与管理操作日志 | 否 |

部署时显式设置STORAGE_ROOT为项目根目录的storage绝对路径，并挂载到Java容器固定目录；不要由apps/api的工作目录推断一个不同storage。运行数据加入/storage/的Git忽略规则，代码构建和重新部署不覆盖它。

业务文件与图片在运行时创建并加入 Git 忽略。Java初次运行显式初始化受保护的其他分类及默认配置；如果已存在store.json但内容损坏，应停止业务启动并提示恢复，不自动清空。

## 2 单进程文件写入

Java启动先获得独立store.lock的排他文件锁，再读取store.json；第二个指向同目录的写进程拒绝启动。每次业务写入使用同一个进程内锁，序列为：读取当前快照、检查对象版本、在新副本修改、验证整个候选对象、完整写同目录临时文件、刷写、原子替换正式JSON、替换内存引用、返回成功。

不能先把内存改成功再慢慢写文件，也不能直接截断正式文件后逐段写入。不加入日志回放、事务框架或后台持久任务。最终本地文件系统需实际支持同目录原子替换；不满足时先修部署目录，不能假装已保证安全保存。

若进程在替换前退出，正式文件仍为旧版；替换后退出，重启读到新版。响应不确定时刷新查看。极端断电、磁盘损坏不承诺零损失，使用备份恢复。临时文件不自动当成最新业务数据读取。

读请求只捕获一次不可变Store引用，一次请求的作品、分类和站点内容都从它解析。draft.content和published.content不能共享可变子对象，数组与图片块也要独立复制。

## 3 图片与请求边界

文件最多20,000,000字节；multipart整体上限初值21MB，留出协议开销。浏览器默认逐张上传，Java图像处理并发1；忙则提示稍后重传，不排持久队列。管理草稿JSON上限512KB，公开浏览请求上限256KB。

先读尺寸和格式，限制40MP及单边20000像素后才完整解码，拒绝SVG、动画、截断和伪装格式。HTTP超时不等于解码线程已停止，解码许可在实际结束后释放；进程异常允许人工重启。重传可以产生未引用副本，不增加去重平台。

先写tmp，处理并生成全部显示图，移动到正式资源目录，最后登记Asset到JSON；没登记成功的文件不能公开访问。目录名和文件名仅使用服务端生成编号，用户原始文件名不参与路径拼接。文件内容不覆盖，改首图或排序只改JSON。

显示图矫正方向、转sRGB、去元数据；透明图保留透明度。JPEG、透明PNG、静态WebP、横竖图与带色彩配置文件都要用真实作品检查；Java插件读WebP不代表能够原样写WebP，首期输出JPEG或PNG即可。

## 4 基本登录和媒体权限

唯一维护者用户名与BCrypt哈希放项目外部注入或不入Git的私密环境配置，禁止默认密码。Spring Security负责登录、退出、会话与CSRF；生产HTTPS，Cookie为Secure、HttpOnly、SameSite=Lax，空闲30分钟失效。重启需要重新登录。

浏览器只访问同一站点。Nginx将/api和/media转给Java，不把storage设为静态目录。公共图片每次检查当前可见作品或已发布站点配置是否引用该Asset，再读指定显示档位；后台待用图片需登录，原图路径不返回访客。

公开JSON不得序列化整个Store或Work管理对象；显式映射公开快照和媒体URL，去掉draft、内部编号、文件路径与账号配置。未发布、已下架和不存在的作品统一不可见。

## 5 备份与人工恢复

每天复制一次完整store.json与正式images/originals、images/display目录到机器外。首期使用 scripts/backup.sh 短暂停止 API 后打包，再恢复原来运行的 API；停服保证 JSON 和图片一致，不增加在线备份接口或服务。会话随 API 重启失效，维护者需重新登录。包生成失败不视为备份成功。

备份包不包含tmp、logs和backups本身，避免递归打包。保留7个日备份和4个周备份，落本机只是中转，必须另存到机器外。原图、显示图与JSON缺一不可；恢复不能只恢复图片目录。

恢复时停止Java，保留当前损坏文件，替换成一份完整已核验的JSON和对应图片，再启动并检查3个作品、首图顺序及配置。没有数据库导入、后台任务续跑或共享会话恢复。

初始目标最多丢失24小时已保存数据，恢复目标4小时，待实际演练。首期不自动永久删除图片；若需人工清理未引用文件，先备份并停写核对当前draft、published和site引用。取消历史版本表后，历史恢复依赖备份。

## 6 数据与图片重点验收

| 场景 | 预期 |
| --- | --- |
| 保存后重启Java | 作品、分类、首图、排序与配置恢复；需要重新登录 |
| 只改草稿、重新启动 | 公开仍为旧版，不能因重载文件把草稿当公开 |
| 保存过程中模拟文件写失败或磁盘满 | 不返回成功、不更新内存、不截断正式JSON |
| 在文件替换前后分别杀进程 | 重启得到完整旧版或完整新版，不读取半文件 |
| 同一数据目录启动两个Java实例 | 第二个实例拒绝写入并退出启动 |
| 两个标签页保存同一草稿版本 | 一个成功，另一个409，不能静默覆盖 |
| 发布后下架，再重放旧发布请求 | 状态版本冲突，不重新公开 |
| 第一次加入图片 | 自动设首图，sortOrder=1 |
| A、文字T、B、C中设C为首图 | C、A、文字T、B；coverImageId指向C，其他相对顺序不变 |
| 横竖比例不同的图片互换首图、删除后提升 | 裁剪与焦点基于新图重置；封面预览3:4且不沿用旧参数 |
| 普通图文块排序 | 重编号且首图固定首位，详情与放大顺序一致 |
| 删除首图且仍有图片 | 确认后提升剩余第一张；无图片时只可保存草稿 |
| 同一Asset复用于两个作品 | 两件作品的首图和顺序独立，磁盘文件不移动 |
| 改首图和顺序但不发布 | 访客首页、列表、详情保持原公开版 |
| 分类有当前引用 | 删除被拒绝；停用原关联可保留；改名即生效 |
| 草稿图片匿名访问 | 拒绝；原图目录和store.json也不能直接访问 |
| 一个文件上传失败或取消晚到 | 成功项不重传，旧回调不插入作品，允许无引用副本 |
| 25件作品浏览与详情返回 | 12、24、25；切分类重置首批；返回恢复后重新核对公开状态 |
| 从机器外备份恢复 | 元数据与图片匹配，首图、正文顺序及公开状态正确 |

图像边界验证20MB、40MP、单边限制、横竖方向、透明度和色彩；界面核对320/390/768/1440宽度及减少动画。单图作品应有可用详情和放大，不多出重复首图或空白正文。

## 7 验证工具与开发分段

单元测试使用临时本地目录和真实文件操作验证JSON保存、重启加载、版本冲突及首图排序，不使用Testcontainers或数据库测试。并发与杀进程用例仅针对一个Java写进程与文件锁，不扩展为集群故障测试。

开发顺序为：JSON存取与模型校验、登录上传、作品草稿和首图顺序、发布下架、分类配置、公开页面和动效、备份恢复。每段只做与该功能相关的必要验证。

2核4GB作为试运行起点，Java图像并发1，内存和完整JSON写入耗时须用真实数据测量。先验证3个真实项目与100件作品；接近1000件时再评估是否拆文件，不提前引入数据库。磁盘达到80%或反复上传失败时人工检查即可。
